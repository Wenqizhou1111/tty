# Windows 输入法框架：怎么做

一份「从零做一个 Windows 输入法」的完整路线图，配套一份可编译的 TSF 骨架代码。
文档里所有注册表结构都**在本机（Windows 11 26200）真实注册的输入法上核对过**，
不是凭记忆写的——这点很关键，因为 TSF 的注册细节在网上的二手资料里错得很多。

> 阅读顺序建议：

> 想搞懂原理 → 从第 1 章顺序读
> 已经在写了但卡住 → 直接看第 11 章「症状 → 原因 → 对策」

## 1. 先选路线：三条路，选错会白干一个月

| | **IMM32**（老 IME） | **TSF / CTF**（本文选择） | **本地服务型 IME** |
| --- | --- | --- | --- |
| 技术形态 | 一个 `.ime` DLL + `Keyboard Layouts` 注册表项 | `InprocServer32` 的 COM DLL，注册进 `CTF\TIP` | `LocalServer32` 的 EXE，独立进程 |
| 典型例子 | 老版紫光、部分日文 IME | `imjptip.dll`、`TableTextService.dll` | **微软拼音 `ChsIME.exe`**（Win8 之后） |
| 能拿到光标/上下文 | 只能拿到很有限的信息 | 完整的 `ITfContext`：文本、选区、只读状态 | 同 TSF（它本身就是 TIP） |
| 现代应用兼容性 | 差：UWP/WinUI/部分 Chromium 收不到组合事件 | 好 | 最好（进程隔离，崩了不拖死应用） |
| 崩溃影响 | 拖死宿主应用 | 拖死宿主应用 | 只死自己 |
| 开发成本 | 低 | 中 | 高（多一层 IPC 与生命周期） |
| 适合 | 维护老项目 | **新项目默认选它** | 大型商业输入法 |

**结论**：新项目用 TSF。本机实测也印证了这个趋势——微软自己的拼音/五笔已经是
`LocalServer32`（`C:\Windows\System32\InputMethod\CHS\ChsIME.exe`），
而进程内 DLL 型的 TIP 仍然大量存在（日文 `imjptip.dll`、韩文 `imkrtip.dll`、
表驱动输入法 `TableTextService.dll`），骨架走的是后者：**最好调试、最少基础设施**。

有一点必须知道：TSF 输入法在「不支持 TSF 的老程序」里靠 **CUAS**
（Cicero Unaware Application Support，Cicero 是 TSF 的旧名）兜底。
本机 `HKCU\SOFTWARE\Microsoft\CTF\CUAS\DefaultCompositionWindow` 存着 `Left/Top`，
就是这套兜底机制留下的痕迹（见第 10.5 节）。

## 2. 进程模型：为什么输入法是「钻到每个应用里的 DLL」

这是理解一切坑的前提：

```
       ┌──────────────────────────┐         ┌──────────────────────────┐
       │   记事本.exe (x64)        │         │  浏览器.exe (x64)         │
       │  ┌────────────────────┐  │         │  ┌────────────────────┐  │
       │  │    MyIme.dll       │  │         │  │    MyIme.dll       │  │  ← 每个进程各一份
       │  │  （文本服务对象）    │  │         │  │  （文本服务对象）    │  │     各自独立的实例
       │  └─────────┬──────────┘  │         │  └─────────┬──────────┘  │
       │        msctf.dll (TSF)    │         │        msctf.dll          │
       └──────────────────────────┘         └──────────────────────────┘
                     ▲                                    ▲
                     └──────────── 用户按键 ───────────────┘
```

直接后果，每一条都会变成真实 bug：

1. **你的代码在每个进程里各跑一份**，进程之间不共享内存。
   所以：词典要按进程加载、用户词库要么落盘要么走独立服务进程。
2. **线程模型是 Apartment**，TSF 给每个线程创建一个文本服务对象
   （`OnActivateEx` 在线程上被调用）。所以你的对象**不能跨线程用**
   ——本骨架用 `m_dwOwnerThreadId` 挡住「跨线程销毁窗口」这类崩溃。
3. **你的崩溃 = 宿主的崩溃**。记事本崩了怪你，这是进程内 TIP 的天生代价。
   任何 `new`/文件读取/COM 调用都要能容错。
4. **位数必须全覆盖**：64 位系统上仍有 32 位进程（老程序、某些 Office 加载项）。
   只注册 x64 DLL，这些进程里输入法不存在。
5. **权限边界**：以管理员运行的程序（`以管理员身份运行` 的终端、任务管理器）
   会拒绝加载普通用户可写路径下的 DLL——所以 DLL **必须**装在
   `%ProgramFiles%` 这种管理员可写、普通用户只读的位置。

## 3. 总体架构：四层，各有明确边界

```
┌───────────────────────────────────────────────────────────────────────┐
│ ① TSF 接口层（src/TextService.*, EditSession.*, DisplayAttribute.*）   │
│    只干两件事：把 TSF 的事件翻译成引擎输入；把引擎的输出变成文档操作     │
│    它不懂拼音，也不画界面                                              │
└───────────────┬───────────────────────────────────┬───────────────────┘
                │ KeyInput / StepResult             │ 候选列表
┌───────────────▼───────────────────┐   ┌───────────▼───────────────────┐
│ ② 引擎层（src/Engine.*）           │   │ ④ 呈现层（src/CandidateWindow）│
│    纯逻辑、无 Win32 依赖           │   │    自绘 HWND，只管画和摆位置    │
│    按键 → 组合状态 → 候选 → 上屏    │   │    不碰文档、不碰引擎状态       │
└───────────────┬───────────────────┘   └───────────────────────────────┘
                │ 查询
┌───────────────▼───────────────────────────────────────────────────────┐
│ ③ 数据层（src/Dictionary.*、data/dictionary.txt）                      │
│    码表/词典：切分、精确查、前缀查。进程级共享、只读                     │
└───────────────────────────────────────────────────────────────────────┘
```

**为什么要把引擎独立出来**（这是本骨架最重要的设计决定）：

- 输入法 80% 的 bug 在引擎里（切分错、候选顺序错、翻页越界、丢输入），
  而不是在 TSF 里。引擎没有 Win32/TSF 依赖，就能用 `EngineTest.exe` 毫秒级跑完，
  不用装输入法、不用重启、不用手打——见 `tests/EngineTest.cpp`。
- 换方案（拼音 → 双拼/五笔/云候选）只改 ②③ 两层，① 层一行不动。

## 4. 一个按键的完整旅程（把这张时序图背下来，80% 的问题都能定位）

```
用户敲 'n'
   │
   ├─▶ ITfKeyEventSink::OnTestKeyDown      ← 「这个键你要吗？」必须马上回答
   │      要 → *pfEaten = TRUE，然后立刻返回
   │      ⚠️ 这里【不要】调 PreserveKey —— 它注册的是热键（见 6.4），
   │         普通按键只要回答 TRUE，框架就会接着调 OnKeyDown
   │
   ├─▶ ITfKeyEventSink::OnKeyDown          ← 「那你处理它」
   │      ① Engine::Step(KeyInput) → StepResult
   │      ② 按 StepResult 行动：
   │         commitText 非空 → 提交
   │         cancelComposition → 取消组合
   │         changed → 刷新组合文字
   │
   ├─▶ 刷新组合 = 编辑会话（ITfContext::RequestEditSession）
   │      ┌ DoEditSession(ec) 只有在这里才持有文档锁 ec ─────────────┐
   │      │ 没有组合 → ITfContextComposition::StartComposition       │
   │      │ 有组合   → ITfRange::SetText("nih")                      │
   │      │            ITfRange::SetGUID(GUID_PROP_ATTRIBUTE, atom)  │ ← 虚线下划线
   │      │            光标收窄到组合末尾 + SetSelection              │
   │      └──────────────────────────────────────────────────────────┘
   │
   └─▶ 候选窗
          先发起一个「只读同步编辑会话」用 ITfContextView::GetTextExt 取位置
          （GetTextExt 需要文档锁！这是新手最容易漏的一点）
          再 SetWindowPos 摆窗口（WS_EX_NOACTIVATE，绝不抢焦点）
```

关键结论：**所有对文档的读写都发生在编辑会话里**。你在 `OnKeyDown` 里
直接拿着 `ITfContext*` 去 `SetText` 一定会失败（`TS_E_NOLOCK`）。

## 5. 接口清单：谁在什么时候被调用

| 接口 | 实现处 | 什么时候被调用 | 你必须做什么 |
| --- | --- | --- | --- |
| `ITfTextInputProcessorEx::OnActivateEx` | `TextService.cpp` | 用户切到这个输入法时 | 拿到 `ITfThreadMgr` + `TfClientId`，挂上所有事件槽 |
| `ITfTextInputProcessor::OnDeactivate` | 同上 | 切走/关闭时 | 反注册、结束组合、**释放所有引用** |
| `ITfThreadMgrEventSink::OnSetFocus` | 同上 | 焦点在文档/控件间移动 | 结束当前组合，切到新 `ITfContext` |
| `ITfThreadFocusSink::OnKillThreadFocus` | 同上 | 整个线程失去焦点 | 结束组合、关候选窗、取消按键保留 |
| `ITfKeyEventSink::OnTestKeyDown` | 同上 | 每个按键，**先于**应用 | 立刻回答吃/不吃，然后返回（别做别的事） |
| `ITfKeyEventSink::OnKeyDown` | 同上 | 你答「吃」之后 | 驱动引擎，产出组合/上屏 |
| `ITfKeyEventSink::OnPreservedKey` | 同上 | 你注册的**热键**被按下 | 处理热键（骨架用它做中英切换，见 6.4） |
| `ITfCompositionSink::OnCompositionTerminated` | 同上 | **别人**把你的组合结束了 | 只清理本地状态，**绝不能**再调 EndComposition |
| `ITfDisplayAttributeProvider` | `DisplayAttribute.cpp` | TSF 要画组合文字时 | 提供显示属性（颜色/下划线） |
| `ITfEditSession::DoEditSession` | `EditSession.cpp` | 文档锁到手时 | 在这里才读写文档 |
| `IClassFactory` | `dllmain.cpp` | TSF 创建文本服务对象 | `new CTextService` |
| `IEnumTfDisplayAttributeInfo` | `DisplayAttribute.cpp` | TSF 枚举显示属性 | 枚举两个属性即可 |

按需再实现的（骨架没做，见第 13 章扩展清单）：
`ITfCompartmentEventSink`（监听中英开关变化）、`ITfTextEditSink`（监听应用改文档）、
`ITfCandidateListUIElement`（把候选交给 TSF 的 UIManager 画，见 8.1）、
`ITfFunctionProvider`（给应用提供额外查询能力）。

> 注意一个常见误解：**`ITfUIElementSink` 是「应用」实现的接口，不是输入法实现的**。
> 输入法这边要做的是实现 `ITfCandidateListUIElement` 一族接口，再用
> `ITfUIElementMgr` 把 UI 元素推给系统；真正消费它的是宿主应用。

## 6. 组合（Composition）与编辑会话：TSF 最容易劝退的地方

### 6.1 三个对象的关系

```
ITfContext（文档/控件）
   └─ ITfContextComposition::StartComposition(pContext, pRange, pSink, &pComposition)
          └─ ITfComposition（一个「正在编辑中的范围」）
                 └─ GetRange(&pRange) → ITfRange（真正能 SetText 的东西）
```

- 组合文字**就是文档里的真实文字**，不是悬浮层。用户看到的 `nihao` 真的在
  文档缓冲区里，只是被标记成「组合中」。
- 所以：**上屏 = 把组合范围替换成最终文字，然后结束组合**；
  **取消 = 把组合范围清空，然后结束组合**（本骨架在 `CancelComposition`
  里先 `SetText("")` 再 `EndComposition`——少了这一步，用户按 Esc 后
  文档里会留下 `nihao` 五个字母，这是非常常见的实现 bug）。
- 显示属性（虚线下划线）挂在 range 上，上屏/取消时要摘掉，否则结果文字
  会一直带着「未上屏」的样子。
  **摘的过程有个坑**：`ITfRange` **没有** `ClearGUID` 方法（网上有资料这么写，
  是错的——`ITfRange` 上只有 `SetGUID` / `GetGUID`）。清除必须走属性对象：

  ```cpp
  ITfProperty* pProp = nullptr;
  pContext->GetProperty(GUID_PROP_ATTRIBUTE, &pProp);
  VARIANT var; VariantInit(&var);          // VT_EMPTY = 清除
  pProp->SetValue(ec, pRange, &var);
  ```

  骨架把它封装成了 `CTextService::ClearDisplayAttribute()`。
  （设置属性时骨架用的是更简洁的 `ITfRange::SetGUID(ec, GUID_PROP_ATTRIBUTE, atom)`，
  它等价于「取属性 + SetValue」，两种写法都对。）

几个容易被忽略但很关键的契约细节（骨架已按此实现）：

1. **拿插入点范围优先用 `ITfInsertAtSelection`**：
   `QI(IID_ITfInsertAtSelection)` → `InsertTextAtSelection(ec, TF_IAS_QUERYONLY, NULL, 0, &pRange)`。
   它只查询不改文档，而且**应用当前没有选区时也能拿到插入点**，
   比只用 `ITfContext::GetSelection` 稳。骨架的做法是「先试它，失败再退回选区」。
2. **`StartComposition` 返回 `S_OK` 但组合指针为 NULL = 宿主拒绝了这次组合**。
   必须当成失败处理，否则后面 `SetText` 会拿到空指针。
3. 组合范围会自动带上 `GUID_PROP_COMPOSING`（由 TSF 管理，结束组合时它自己清），
   你不用管；你只需要管自己的 `GUID_PROP_ATTRIBUTE`。
4. `ITfComposition::EndComposition(ec)` **不会释放组合对象**，指针要自己 Release。
   骨架用 `ComPtr<ITfComposition>` 自动管理。
5. `ITfComposition::GetRange(&pRange)` **没有 ec 参数**（不需要文档锁），
   而 `ITfRange::SetText/SetGUID` 都需要 ec。
6. 去激活时也要摘显示属性：如果组合从没被正常结束过，
   属性会留在文档里。骨架在 `ResetCompositionState()` → `CancelComposition()`
   路径里统一处理。

### 6.2 编辑会话的三种模式

| 模式 | 用途 | 本骨架里的调用 |
| --- | --- | --- |
| `TF_ES_SYNC \| TF_ES_READWRITE` | 必须立刻生效 | 开始组合、上屏、取消 |
| `TF_ES_ASYNCDONTCARE \| TF_ES_READWRITE` | 刷新组合文字 | 每敲一个字母 |
| `TF_ES_SYNC \| TF_ES_READ` | 只读查询 | 取候选窗位置（`GetTextExt`） |

### 6.3 失败必须能兜住（这一节决定你的输入法「稳不稳」）

`RequestEditSession` 会通过出参告诉你会话到底跑没跑：

- **`TS_E_NOLOCK`**：文档正被别人锁着。对策：本次不改，**保持输入状态**，
  下次按键重试。绝不能把用户敲的字母丢掉。
- **`TS_E_SYNCHRONOUS`**（部分文档不支持同步会话）：退回异步重试一次，
  骨架在 `RequestEditSession` 里已实现这个 fallback。
- **`StartComposition` 拿不到选区**：文档只读/没焦点。对策：放弃本次组合，
  下次再试（骨架里 `StartComposition` 分支直接返回失败，状态机保持不动）。

结论：**编辑会话是「可能失败的操作」，不是函数调用**。
本骨架为此专门留了 `m_fCancelPending`：取消失败时不清掉组合指针，
而是打标，下次按键重试——直接 `Reset()` 会留下一个没人管的组合，
文档里就会浮着一串永远不消失的字母。

### 6.4 `PreserveKey` ≠ 「保证 OnKeyDown 送达」（最常见的 TSF 误传）

网上大量中文资料（包括一些博客和 AI 生成的内容）说：
「在 `OnTestKeyDown` 里调 `ITfKeystrokeMgr::PreserveKey`，才能保证收到 `OnKeyDown`」。
**这是错的**，而且照着写会真的出问题——本骨架第一版就踩过：

- `PreserveKey` 注册的是**保留键（preserved key）**，也就是**热键**。
  它被按下后走的是 `ITfKeyEventSink::OnPreservedKey(rguid)`，
  **不经过 `OnKeyDown`**。传给 `PreserveKey` 的 GUID 就是 `OnPreservedKey`
  收到的那一个——两者是一对。
- 对普通字母键调它，等于每次敲键都在注册一个热键，行为必然错乱。
- 正确的做法：**同步处理按键时什么都不用调**。`OnTestKeyDown` 返回
  `*pfEaten = TRUE` 之后，框架就会调 `OnKeyDown`。

只有两种场景真的需要它：

1. **注册热键**（骨架在 `OnActivateEx` 里注册 `Ctrl+Space` 做中英切换，
   在 `OnPreservedKey` 里处理）；
2. **按键要异步处理**：你需要把键「按住」不让应用看到，处理完再
   `UnpreserveKey`。

微软教学示例 `textservice-step06` 的原始用法（这是标准的「注册热键」范式）：

```cpp
static const TF_PRESERVEDKEY c_pkeyOnOff = { 0xC0,      TF_MOD_ALT };              // Alt+~
static const TF_PRESERVEDKEY c_pkeyF6    = { VK_F6,     TF_MOD_ON_KEYUP };         // 抬键触发
// Activate():   AdviseKeyEventSink(...) 之后，逐个 PreserveKey
pKeystrokeMgr->PreserveKey(tid, GUID_PRESERVEDKEY_ONOFF, &c_pkeyOnOff, desc, len);
// Deactivate(): 逐个 UnpreserveKey，再 UnadviseKeyEventSink
```

`TF_PRESERVEDKEY { UINT uVKey; UINT uModifiers; }`，修饰位：
`TF_MOD_ALT 0x1`、`TF_MOD_CONTROL 0x2`、`TF_MOD_SHIFT 0x4`、`TF_MOD_RALT 0x8`、
`TF_MOD_RCONTROL 0x10`、`TF_MOD_RSHIFT 0x20`、`TF_MOD_LALT 0x40`、
`TF_MOD_LCONTROL 0x80`、`TF_MOD_LSHIFT 0x100`、`TF_MOD_ON_KEYUP 0x200`、
`TF_MOD_IGNORE_ALL_MODIFIER 0x400`。
重复注册同一个热键会返回 `TF_E_ALREADY_EXISTS`（说明组合键已被占用）。

骨架的热键实现顺便演示了中英切换的正确姿势：写 TSF 的
`GUID_COMPARTMENT_KEYBOARD_OPENCLOSE` compartment（`ITfCompartment::SetValue`），
而 `ShouldEatKey` 读的正是同一个 compartment，所以切换立刻生效。
注册失败（比如组合键已被系统占用）不是错误，日志里会写清原因。

除中英开关外，`ShouldEatKey` 还检查了 `GUID_COMPARTMENT_KEYBOARD_DISABLED`
（宿主/系统禁用键盘时不吃键）——这也是微软 SampleIME 的判定条件之一。

常用错误码（已核对）：`TS_E_NOLOCK` 与 `TF_E_NOLOCK` 是同一个值 `0x80040201`；
`TF_E_SYNCHRONOUS = 0x80040208`、`TF_E_READONLY = 0x80040209`、
`TF_E_NOLAYOUT = 0x80040206`；`TF_S_ASYNC = 0x00040300` 是**成功**码
（判断时用 `FAILED()` 宏，不要写 `== S_OK`，否则会把异步成功当成失败）。

## 7. 显示属性：虚线下划线是怎么来的

三步，缺一不可：

1. 文本服务实现 `ITfDisplayAttributeProvider`
   （TSF 用 `QueryInterface` 从文本服务对象上取它，所以放在同一个类里最省事）。
2. 激活时把自己定义的属性 GUID 注册进 `ITfCategoryMgr::RegisterGUID`，
   换回一个 `TfGuidAtom`（`TextService.cpp` 的 `OnActivateEx` 第 3 步）。
3. 设置组合文字时用 atom 打标：
   `ITfRange::SetGUID(ec, GUID_PROP_ATTRIBUTE, atom)`。

属性 GUID 是**你自己定义**的（骨架里是 `kGuidDisplayAttrInput` /
`kGuidDisplayAttrConverted`），不是系统常量——很多资料把它说成系统 GUID，
是错的。`TF_DISPLAYATTRIBUTE` 里能控制文字色/背景色/下划线样式
（本骨架：未上屏 = 灰色点线下划线，已转换 = 蓝色实线）。

## 8. 候选窗：两个流派 + 三个必踩的坑

### 8.1 自绘窗口 vs TSF 的 UIManager

| | 自绘 HWND（骨架采用） | 交给 TSF 的 UIManager |
| --- | --- | --- |
| 你要实现的 | 一个窗口类 + 绘制 + 定位 | `ITfCandidateListUIElement`（含 `ITfCandidateListUIElementBehavior`）+ 用 `ITfUIElementMgr` 推元素 |
| 控制力 | 完全（皮肤、动画、多行、鼠标点选） | 受框架约束 |
| 工作量 | 自己写绘制/定位/DPI | 接口一族较繁琐，绘制交给系统 |
| 全屏游戏/特殊 UI | 可能被压住（要处理 Z 序） | 由系统统一处理 |
| 与系统观感一致 | 要自己模仿 | 天然一致 |

两者在真实产品里都存在——**微软自己的 SampleIME 两套都写了**。
骨架选自绘，因为「定位 + 绘制」的完整流程看得见、好调试。
再次强调：消费候选 UI 的 `ITfUIElementSink` 是**应用**侧的接口，
输入法这侧不实现它。

### 8.2 定位：`GetTextExt` 需要文档锁

真实 bug 现场：在 `OnKeyDown` 里拿 `ITfContextView::GetTextExt` 取光标位置
→ 返回 `TS_E_NOLOCK` → 候选窗跑到屏幕角落。

正确做法（骨架 `EditAction::QueryAnchor`）：开一个**只读同步编辑会话**，
在 `DoEditSession` 里取位置；位置存到成员变量，会话结束后再摆窗口。
另外这几个都是实测过的坑：

- **`GetTextExt` 返回 `S_OK` 但矩形是全 0** 是合法情况（文档还没渲染、
  窗口最小化、文本不在可视区）。必须显式判断并当作「拿不到位置」，
  否则候选窗会跑到屏幕左上角——这是最常见的候选窗 bug。
- 折叠范围（起点=终点）返回的矩形宽度可能是 0，要补一个最小尺寸；
- 取不到位置时的退路：`ITfContextView::GetScreenExt`（整个视图区域），
  再退到鼠标位置（骨架的 `MoveToAnchor` 在 `anchorValid == false` 时用光标位置）；
- 拿到的坐标是**屏幕坐标**，还要夹到 `MONITORINFO::rcWork` 里，
  否则贴边时会跑出屏幕；下方放不下就翻到光标上方；
- `GetTextExt` 的其它失败码：`TF_E_NOLAYOUT`（没有布局信息）、
  `TF_E_NOLOCK`（cookie 不对）。
- **位置会变**：用户滚动、缩放、窗口移动后候选窗就不动了。
  正确做法是实现 `ITfTextLayoutSink`：在 `ITfDocumentMgr` 上
  `ITfSource::AdviseSink(IID_ITfTextLayoutSink, ...)`，
  收到 `TF_LC_CHANGE(1)` 时再跑一次只读会话重新取位置并移动窗口，
  `TF_LC_DESTROY(2)` 时把候选 UI 拆掉。骨架没做（见第 13 章 P1）。
- **候选窗要挂在宿主窗口上**：`ITfContextView::GetWnd(&hwnd)` 拿到应用焦点窗口，
  把它作为候选窗的 **owner**（不是 parent）。这样候选窗一定浮在应用上方，
  并且随应用窗口一起销毁。骨架的 `CandidateWindow::SetOwner()` 做的就是这件事，
  同时用 `IsWindow()` 挡住「宿主窗口先销毁导致句柄失效」这一类问题。

### 8.3 绝对不能抢焦点

候选窗用 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST`，
只调 `ShowWindow(SW_SHOWNOACTIVATE)` / `SetWindowPos(..., SWP_NOACTIVATE)`，
并在 `WM_MOUSEACTIVATE` 里返回 `MA_NOACTIVATE`。
只要你调一次 `SetFocus`，文档就会失焦，组合会被 `OnCompositionTerminated` 干掉。

> 一个有趣的对照：**微软的 SampleIME 并没有用 `WS_EX_NOACTIVATE`**，
> 它靠 `WS_EX_TOOLWINDOW` + `SW_SHOWNA` + `SWP_NOACTIVATE` 达到目的。
> 两种做法事实标准上都成立；骨架多加了 `WS_EX_NOACTIVATE`，
> 因为「绝不激活」这件事多一道保险更划算。另外注意 `ShowWindow` 要用
> `SW_SHOWNA`（no activate）而不是 `SW_SHOW`。

### 8.4 DPI

骨架用 `GetDeviceCaps(LOGPIXELSY)` 取系统 DPI 并按比例缩放字号/间距，
够用但不完美：跨显示器拖动时不会自动换 DPI。

需要说明的是：**微软官方文档从未规定 `GetTextExt` 的 DPI 语义**，
微软自己的 SampleIME 也**完全没做 DPI 处理**（没有 `GetDpiForWindow`、
没有 `SetThreadDpiAwarenessContext`）。所以这块属于「工程经验」而非「文档要求」：
IME 的 DLL 跑在应用进程里，如果应用是 per-monitor DPI 感知而你是系统 DPI 感知，
坐标就可能错位（DPI 虚拟化）。
要做得稳：给 DLL 加 per-monitor v2 清单（或显式设置感知上下文），
用 `GetDpiForWindow` / `GetDpiForMonitor` 计算尺寸与位置。

## 9. 输入引擎：候选到底是怎么来的

骨架的候选生成是「可读优先」的实现，四个来源（`Engine::BuildCandidates`）：

```
输入 nihao
 │
 ├─ ① 切分：用音节表把连续字母切成音节 → ["ni","hao"]
 │     多音节串用「长音节优先」的回溯，' 可作显式分隔（xi'an）
 │     最后一段允许「没打完」：nih → 已确定 ["ni"] + 尾巴 "h"
 │
 ├─ ② 整串精确查：joined = "nihao" → 命中整词「你好」（加分最高）
 │
 ├─ ③ 单字组合：每个音节取前 N 个单字候选
 │      全取首选 → 你好；再逐音节单点替换 → 你号 / 尼好 / 泥好 …
 │
 ├─ ④ 尾巴补全：尾巴 "h" 做前缀查询 → 好/和/号 …，与已确定部分拼接 → 你好、你和 …
 │
 └─ 兜底：一个候选都没有 → 把原样字母当候选（保证空格仍能把 zzz 打出去，不吞输入）
```

排序按分数降序（同分保持稳定顺序），去重按文本保留最高分，
上限 35 条 = 7 条/页 × 5 页；翻页/选字在 `Engine::Step` 里。

**换成别的码表要动哪里**：`data/dictionary.txt` 的「码」不限于拼音音节，
`Dictionary::AddEntry` 会把出现过的键自动并入键集合——所以
`tests/EngineTest.cpp` 里那组 `ab 甲 / ac 乙 / ab ac 甲乙` 能直接跑通，
说明引擎不是拼音专用的。五笔/双拼/仓颉只需换数据文件，
要做「词组优先/动态调频/云候选」则扩展 ②③ 两步。

**已知的简化**（按性价比排序的升级点）：

1. 候选只有「整词命中」和「单字组合」，没有 K-best 路径搜索（Viterbi）。
   `nihao` 没问题，长句（`jintiantianqihenhao`）会明显不如商业输入法。
2. 没有用户词库/词频自适应。
3. 前缀补全的排序用「码越短 + 权重越高」，简单但不够准（输入 `h` 时
   「和」排在「好」前面，这是权重使然，不算错，但体验一般）。
4. 没有模糊音、简拼（`nh` → 你好）、双拼方案。

## 10. 注册与安装：为什么「注册表都写了却看不到输入法」

### 10.1 必须写齐的三块（本机实证结构）

**[1] COM 注册**

```
HKCR\CLSID\{你的CLSID}
    (默认)          = 描述文字
    InProcServer32
        (默认)          = <DLL 完整路径>
        ThreadingModel  = Apartment        ← 必须是 Apartment
```

**[2] TSF 文本服务**

```
HKLM\SOFTWARE\Microsoft\CTF\TIP\{你的CLSID}
    Enable = 1 (DWORD)
    LanguageProfile\0x00000804\{ProfileGUID}
        Description         = 用户看到的名字
        Display Description = @C:\path\to.dll,-资源ID     （可选，做多语言用）
        IconFile            = <图标来源 DLL/EXE>
        IconIndex           = 0 (DWORD)
        Enable              = 1 (DWORD)
        ProfileFlags        = …            （可选：profile 的类别/能力标志）
        HiddenInSettingUI   = …            （可选：是否在设置界面隐藏）
```

> `LanguageProfile` 的完整取值名还有 `ProfileFlags` / `HiddenInSettingUI` 这类
> 可选值（**这两个的语义我尚未逐位验证，用到时请以本机实测为准**）。
> 最小可用集就是上面列出的那五个。

**[3] 分类**（**只写前两块，语言列表里就是看不到你**）

```
HKLM\SOFTWARE\Microsoft\CTF\TIP\{你的CLSID}\Category\Category\{分类GUID}\{你的CLSID}
HKLM\SOFTWARE\Microsoft\CTF\TIP\{你的CLSID}\Category\Item\{你的CLSID}\{分类GUID}
        (默认) = DLL 文件名
```

本机微软拼音与表驱动输入法共有的分类 GUID（全部经官方「预定义分类值」文档核对命名）：

**TIP 类型（必须恰好声明一个）**

> 那是把 COM 的 `CATID_*` 习惯套到 TSF 上的误传；TSF 全部用 `GUID_TFCAT_*`。
> 微软自己的 SampleIME 声明 8 个分类（因为它把这些功能全实现了），
> 骨架只声明 3 个——**声明了做不到的能力，会在对应环境里被激活然后崩掉**。
> 这正是「注册」这一章最值得带走的一条经验。

### 10.2 还要调 COM 接口（官方推荐的安装方式）

只写注册表经常出现「键都在、列表里没有」，因为**语言档案要由 TSF 自己登记**。
官方推荐的三步（都是机器级 HKLM、都要管理员）：

```
① COM 注册                → HKCR\CLSID\{CLSID}\InProcServer32（ThreadingModel = Apartment）
② 语言档案：Vista+ 推荐 ITfInputProcessorProfileMgr::RegisterProfile
③ 分类：ITfCategoryMgr::RegisterCategory(clsid, 分类GUID, clsid)
```

`RegisterProfile` 的完整签名（骨架 `Register.cpp` 用的就是它，失败才退回老接口）：

```cpp
CoCreateInstance(CLSID_TF_InputProcessorProfiles, NULL, CLSCTX_INPROC_SERVER,
                 IID_ITfInputProcessorProfileMgr, (void**)&pMgr);   // {33C53A50-F456-4884-B049-85FD643ECFED}
pMgr->RegisterProfile(rclsid, langid, guidProfile,
                      pchDesc, cchDesc, pchIconFile, cchFile, uIconIndex,
                      hklsubstitute, /*dwPreferredLayout 必须为 0*/ 0,
                      /*bEnabledByDefault*/ TRUE, /*dwFlags*/ 0);
```

- `bEnabledByDefault = TRUE` 是「装完立刻能用」的关键。
- `dwFlags` 可用 `TF_RP_HIDDENINSETTINGUI`(0x2) / `TF_RP_LOCALPROCESS`(0x4) /
  `TF_RP_LOCALTHREAD`(0x8) / `TF_RP_SUBITEMINSETTINGUI`(0x10)。
- 老式等价路径（XP 时代，骨架作为兜底保留）：
  `ITfInputProcessorProfiles::Register` + `AddLanguageProfile`。

**一个容易踩空的名字**：不存在 `ITfInputProcessorProfileMgr::EnableProfile`。
`ITfInputProcessorProfileMgr` 只有 `ActivateProfile` / `DeactivateProfile` / `EnumProfiles` /
`GetActiveProfile` / `GetProfile` / `RegisterProfile` / `ReleaseInputProcessor` / `UnregisterProfile`。
要「启用」只能用：

- `ITfInputProcessorProfiles::EnableLanguageProfile`（**当前用户**，骨架用这个）
- `ITfInputProcessorProfiles::EnableLanguageProfileByDefault`（**所有用户**）
- 或 `ITfInputProcessorProfileMgr::ActivateProfile(..., TF_IPPMF_ENABLEPROFILE)`（`0x00000001`）

反过来卸载：`UnregisterProfile` → `EnableLanguageProfile(FALSE)` → `RemoveLanguageProfile`
→ `Unregister` → `UnregisterCategory` → 再删注册表键。**顺序反了会留下悬挂项。**

想把它设成某语言的**默认**输入法，要用
`ITfInputProcessorProfiles::SetDefaultLanguageProfile`——
微软明确写了「不要直接改注册表来设置默认键盘」。

### 10.2.1 注册路径 vs 用户选择：HKCU 里那份是什么

容易混淆的一点：**同一个 CLSID 在 HKCU 下也有一份**。
本机实测 `HKCU\SOFTWARE\Microsoft\CTF\TIP\{CLSID}` 只对**当前选中/正在用**的
输入法存在，记录的是用户态状态（启用与否、选中哪个 profile），
默认 profile 的选择在 `HKCU\SOFTWARE\Microsoft\CTF\Assemblies\0x00000804\{分类GUID}\`
下的 `Default` / `Profile` / `KeyboardLayout` 几个值里。

**结论**：注册只写 HKLM；不要去写 HKCU 的那一份，
那是系统根据用户操作自己维护的，手写进去会被覆盖甚至造成状态不一致。
（有红队研究实测过：只在 HKCU 注册的 TIP「不产生可用的插件」，
TSF 输入法必须注册在 HKLM 才能工作。）

### 10.3 位数：x86 也要注册

`HKCR\CLSID\...\InProcServer32` 有 32/64 两个视图，由写它的进程位数决定：

- 64 位 DLL → 用 `C:\Windows\System32\regsvr32.exe`
- 32 位 DLL → 用 `C:\Windows\SysWOW64\regsvr32.exe`（会自动写进 `WOW6432Node`）

位数用反了，注册表看着「写成功了」，但对应位数的进程永远加载不到你。
`install.ps1` 已经按这个规则分派，并会检查两边的注册结果。

### 10.4 注册之后为什么要注销/重启才看得到

TSF 会缓存输入法列表（`HKCU\SOFTWARE\Microsoft\CTF\SortOrder\*`、
`AssemblyItem\0x00000804\{34745C63-...}` 就是排序状态）。
新注册的 TIP 有时不会立刻出现在 Win+Space 列表里。经验做法：
注销再登录；或者注册完手动跑一次语言设置的枚举来刷新。

### 10.5 老程序的兜底：CUAS

不支持 TSF 的应用（老 MFC/VB6、部分控制台程序）由 **CUAS** 接管：
它假装成 IMM32，把老应用的输入事件转给 TSF 输入法。官方描述是
「让不认识 TSF 的老应用/控件免费获得高级文本服务」。

已核实的事实：

- CUAS 的实现**就在 `msctf.dll` 里**（`CicBridge::ActivateIMMX`、
  `CicInputContext`、`CtfImeCreateThreadMgr`、`CUIElementSink::BeginUIElement` 等符号）；
  它面向 IMM32 的那一侧是 **`C:\Windows\System32\msctfime.ime`**
  （文件描述「Microsoft Text Frame Work Service IME」）。
- 它自己的**组件 CLSID 至今查不到公开值**：`HKLM\...\CTF\TIP` 下没有 CUAS 条目，
  `Keyboard Layouts` 里也没有引用 `msctfime.ime` 的项。别去找这个 CLSID 了。
- 留下的可观测状态：`HKCU\SOFTWARE\Microsoft\CTF\CUAS\DefaultCompositionWindow`
  （左/上，记录老程序里的组合窗位置）和
  `HKCU\SOFTWARE\Microsoft\CTF\HiddenDummyLayouts`（本机实测 `00000804=00000804`）。

对你的影响：**组合窗位置在这些程序里可能不准**（CUAS 拿不到真实的文本位置，
只能用近似值），这是已知限制，不是你代码的 bug。

调试小技巧：`ImmDisableTextFrameService(dwThreadId)` 可以让某个线程/进程
**强制关掉 TSF** 退回 IMM32 老路——用来判断「这个应用到底走的是 TSF 还是 CUAS」很方便。

## 11. 症状 → 原因 → 对策（这一章最省时间）

| 症状 | 常见原因 | 对策 |
| --- | --- | --- |
| 语言列表里没有我的输入法 | 缺 `Category` 分类键；或没调 `AddLanguageProfile`；或位数注册反了 | 对照 10.1 三块逐个检查；用 `install.ps1 -Action status` |
| 列表里有，切过去敲键没反应 | `AdviseKeyEventSink` 没调用/失败；或 `ShouldEatKey` 全返回 false（中英开关是关的） | 看 DebugView 日志的 `AdviseKeyEventSink` 与 `IsKeyboardOpen` |
| 敲字母，候选窗出来了，但文档里没有字母 | 编辑会话失败（`TS_E_NOLOCK`）；或没实现 `SetCompositionText` 的 `SetText` | 打日志看会话返回值；确认在 `DoEditSession` 里操作 |
| 组合文字没有虚线下划线 | 没注册显示属性 atom，或没 `SetGUID` | 检查 `RegisterGUID` 的返回与 `m_atomInput` 是否非 0 |
| 按 Esc 后文档里留下字母 | 取消时没清空组合文字就 `EndComposition` | 见 6.1：先 `SetText("")` 再结束 |
| 候选窗位置跑到屏幕角落 | 在编辑会话外调 `GetTextExt`（`TS_E_NOLOCK`）；或没夹 `rcWork` | 用只读编辑会话取位置 + 夹工作区 |
| 一切正常，但一敲键应用就失去焦点 | 候选窗抢了焦点 | `WS_EX_NOACTIVATE` + `SWP_NOACTIVATE` + `MA_NOACTIVATE` |
| 输入法在记事本正常，在浏览器里乱 | 浏览器是异步文本存储，同步会话被拒 | 用 `AsyncWrite` 刷新组合；接受「位置偶尔滞后」 |
| 输入法在 64 位程序正常，32 位程序没有 | 只注册了 x64 DLL | 用 SysWOW64 的 regsvr32 注册 x86 版本 |
| 在管理员窗口里完全不生效 | 普通用户可写路径的 DLL 不被高权限进程加载 | 装到 `%ProgramFiles%` |
| 切走再切回来，候选还在 / 字母残留 | 没实现 `OnKillThreadFocus` / `OnSetThreadFocus` 的收尾 | 在那里结束组合、隐藏候选窗 |
| 应用崩溃 | 你的 DLL 崩了，宿主一起死；或跨线程销毁了窗口 | 所有失败路径都要容错；窗口只在创建线程销毁 |
| 按键被「吃掉」但什么都没发生 | `OnTestKeyDown` 说吃但 `OnKeyDown` 没产出；或 test/handle 两处判定不一致 | 保证 `ShouldEatKey` 在两处结果一致；回答吃就必须产出 |
| 敲键行为错乱、有时不触发 OnKeyDown | 在 `OnTestKeyDown` 里对普通键调了 `PreserveKey`（把它当成了「保证送达」） | **删掉那个调用**：`PreserveKey` 是热键注册，回调走 `OnPreservedKey`（见 6.4） |
| 输入法开关（中英）无效 | 没读 `GUID_COMPARTMENT_KEYBOARD_OPENCLOSE` | 骨架 `IsKeyboardOpen()`/`ToggleKeyboardOpen()` 已实现；建议再加 `ITfCompartmentEventSink` 缓存，避免每次按键都查询 |
| 卸载后语言列表里还有一条空的 | 只删了注册表，没撤语言档案 | 见 10.2 的卸载顺序 |

### 12.3 调试进程内 DLL 的实用办法

1. **输出日志优先**：`OutputDebugStringW` + DebugView。不打断、跨进程可见。
2. **确认 DLL 真的被加载进宿主进程**：
   `tasklist /m MyIme.dll`，或用 Process Explorer / Process Monitor
   （筛 `Load Image` 且路径是你的 DLL）。这一步能立刻区分
   「没注册上」和「注册上了但没加载」。
3. **枚举当前注册的输入法（运行时权威）**：
   `ITfInputProcessorProfileMgr::EnumProfiles` / `GetProfile`；
   或 `ITfInputProcessorProfiles::EnumLanguageProfiles`。
   命令行看 `Get-WinUserLanguageList`，UI 看
   「设置 → 时间和语言 → 语言和区域」或经典对话框
   `RunDll32.exe shell32.dll,Control_RunDLL input.dll`。
4. 要断点调试：用 VS 打开本工程 → 调试 → 附加到进程 → 选宿主进程（如 `notepad.exe`），
   需要管理员权限时用 VS 的管理员实例。
   因为 TIP 是**每线程**激活的，断点放在 `DllGetClassObject` / `OnActivateEx` 最有用。
   PDB 放到 DLL 旁边。
5. **系统自带的 ETW 提供程序**（本机实测存在，别自己造日志了）：
   - `Microsoft-Windows-TSF-msctf` `{4FBA1227-F606-4E5F-B9E8-FAB9AB5740F3}`
   - `Microsoft-Windows-TSF-msutb` `{74B655A2-8958-410E-80E2-3457051B8DFF}`
   - `Microsoft-Windows-TSF-UIManager` `{4DD778B8-379C-4D8C-B659-517A43D6DF7D}`
   - `Microsoft-Windows-InputSwitch` `{BB8E7234-BBF4-48A7-8741-339206ED1DFB}`

   用 `wpr -start` / `logman start <名字> -p "Microsoft-Windows-TSF-msctf"` 抓，
   WPA 里看。候选窗不显示、UI 元素不更新这类问题，看 `TSF-UIManager` 最直接。
6. 想快速试错：`regsvr32 /u` 卸载 → 改代码 → 重新编译 → `regsvr32` 注册。
   **注意**：已经加载过你 DLL 的进程不会自动换新版本，重启那些进程（或注销）。
7. 想交叉验证实现（TSF 的另一个开源实现，比文档更适合读代码）：
   Wine 的 `dlls/msctf/`（`inputprocessor.c`、`categorymgr.c`、`context.c`、`range.c`）。
8. 值得跑的兼容性矩阵：记事本、Word、Chrome/Edge（TSF 感知）、
   只支持 IMM32 的老程序（走 CUAS）、UWP 应用、管理员权限的程序、

## 14. 骨架代码导读：读代码的顺序

想改代码，按这个顺序读，最省力：

1. `src/Engine.h`（先看 `StepResult`/`KeyInput` 两个结构，理解「一次按键的产出」）
2. `src/Engine.cpp` 的 `Step()`（状态机）与 `BuildCandidates()`（候选四来源）
3. `src/TextService.cpp` 的 `OnTestKeyDown` / `OnKeyDown` / `ApplyStepResult`
   （TSF 事件怎么进引擎、引擎结果怎么落回文档）
4. `src/EditSession.cpp`（编辑会话外壳）+ `TextService::OnEditSession`
   （**所有文档操作的唯一合法位置**）；
   配套三个小工具函数值得单独看一眼，它们各自对应一个真实的坑：
   `GetInsertionRange()`（`ITfInsertAtSelection` + `TF_IAS_QUERYONLY` 取插入点）、
   `ClearDisplayAttribute()`（用 `ITfProperty::SetValue(VT_EMPTY)` 清属性，
   因为 `ITfRange` 没有 `ClearGUID`）、
   `GetCategoryManager()`（两种取管理器的方式与 COMLESS 环境的关系）
5. `src/Register.cpp`（注册结构，对照第 10 章看）
6. `src/CandidateWindow.cpp`（定位 + 绘制，对照第 8 章看）

另有一个「看起来很怪但很重要」的文件：`src/TsfGuids.cpp`。
它只做一件事——在包含 `msctf.h` 之前先包含 `<initguid.h>`，
让 TSF 那一堆 GUID（`GUID_PROP_ATTRIBUTE`、`CLSID_TF_InputProcessorProfiles`…）
在本模块里**被真正定义**一次。不同 SDK 版本对这些符号放在哪个 lib 里并不一致，
这个 20 行的文件能省掉一整类 `LNK2001 无法解析的外部符号`。
**全工程只能有一个这样的文件。**

改代码时的三条铁律：

- 任何文档读写 → 只能写在 `OnEditSession` 里；
- 任何界面调用（窗口、GDI）→ 只在创建它的线程上做；
- 任何失败路径 → 不许丢用户输入（宁可留着状态下次重试）。

## 15. 本机实证记录（写文档时的核对依据）

以下是从这台 Windows 11（10.0.26200）真实注册表里读出来的一手数据，
用来校正网上流传的错误说法：

1. 微软拼音（`{81D4E9C9-1D3B-41BC-9E6C-4B40BF79E35E}`）是 **LocalServer32**
   （`ChsIME.exe`），不是进程内 DLL；它的 `Category\Category\*` 下有 10 个分类。
2. 进程内 TIP 的确切形态：`表驱动输入法 {E429B25A-E5D3-4D1F-9BE3-0C608477E3A1}`
   → `InProcServer32 = C:\Program Files\Windows NT\TableTextService\TableTextService.dll`，
   `ThreadingModel = Apartment`，TIP 根键下有 `Enable = 1`。
3. `LanguageProfile\0x00000804\{ProfileGUID}` 下真实的取值名是
   `Description` / `Display Description` / `Enable` / `IconFile` / `IconIndex`。
4. 语言档案的 `Enable` 在本机是 0（微软拼音当前未启用），
   说明它是「是否启用」而不是「是否注册」——注册靠键存在，启用靠这个值。
5. `HKEY_CURRENT_USER\SOFTWARE\Microsoft\CTF\TIP\{CLSID}` 也存在，
   记录的是**当前选中/使用**状态，不要误当成注册位置去写。
6. CUAS 的痕迹：`HKCU\SOFTWARE\Microsoft\CTF\CUAS\DefaultCompositionWindow = Left/Top`。
7. 本机**没有**任何 IMM32 型（`Keyboard Layouts\...\IME File`）输入法——
   老路线在这台机器上已经绝迹，进一步支持第 1 章的选型结论。
8. `{34745C63-B2F0-4784-8B67-5E12C8701A31}`（`GUID_TFCAT_TIP_KEYBOARD`）
   在微软拼音和表驱动输入法上都存在，是键盘类 TIP 的必需分类。
9. 不存在名为 `CATID_TSF_TEXT_SERVICE` 的分类——TSF 用的是 `GUID_TFCAT_*` 一族。

### 15.1 一个被广泛传错的知识点（本次已核实并改代码）

`ITfKeystrokeMgr::PreserveKey` **不是**「保证 `OnKeyDown` 被调用」的手段：
它注册的是**保留键（热键）**，触发后回调 `OnPreservedKey`，与 `OnKeyDown` 无关。
骨架第一版照抄了这个错误说法（对每个字母键都 PreserveKey），已修正，详见 6.4。
这个点可以当试金石：凡是告诉你「在 OnTestKeyDown 里 PreserveKey 才能收到 OnKeyDown」
的资料，其余内容也该打个问号。

### 15.2 明确「未验证」的部分（用到时请自行核实）

- `ProfileFlags` / `HiddenInSettingUI` / `DisabledOnTransitory` / `RuntimeClass` 这几个
  语言档案取值的精确语义（本机确实存在这些值名，但没人写清它们的规则）；
- `ITfInputProcessorProfileMgr::UpdateProfile` 的行为；
- TIP 根键默认值（`(Default)`）是否参与显示名解析（**已确认系统 TIP 全都是「未设置」**，
  所以不要依赖它）；
- CUAS 的组件 CLSID —— 公开资料里查不到，实现藏在 `msctf.dll` 里（见 10.5）；
- 控制台模式（`TF_TMAE_CONSOLE = 0x40`）**没有**对应的 `GUID_TFCAT_TIPCAP_*` 分类；
- 系统是否真的为 TIP 应用某种 per-monitor DPI 策略（官方文档没写，示例也没做）；
- `HKLM\SOFTWARE\Microsoft\CTF` 下 `UpdateProfile = "1"` 的用途。

## 16. 已知限制与免责

- 骨架代码在**没有 C++ 工具链的机器上写的**，因此交付时**尚未经过编译验证**。
  已做的自检：`tools/lint_structure.py`（括号配对、成员变量声明、方法声明/定义一致性、
  CMake 引用完整性、include 路径存在性）全部通过。首次编译若报错，大概率是
  SDK 版本差异导致的常量名/结构字段差异，改法见第 11 章与代码注释。

- 候选窗没有做点击选择、没有 per-monitor DPI、没有动画——这些是刻意留白的扩展点。

  （尤其是 `Category` 子树），务必用 `install.ps1 -Action status` 在本机复核。
- 热键固定为 `Ctrl+Space`：如果已被系统或其他输入法占用，注册会失败
  （日志里有提示），改用 Win+Space 或语言栏切换即可；想换键就改
  `TextService::RegisterPreservedKeys()` 里的 `uVKey` / `uModifiers`。

## 17. 附录：环境标志、值名清单与参考资料

### 17.1 `OnActivateEx` 的 `dwFlags`：判断自己被什么环境激活

这些标志和注册时声明的 `GUID_TFCAT_TIPCAP_*` 分类一一对应——
你声明了哪条能力，系统才可能在对应的环境下这样激活你。
骨架把这段翻译成文字打进了日志（`DescribeActivateFlags()`）。

| 标志 | 值 | 含义 | 对应分类 |
| --- | --- | --- | --- |
| `TF_TMAE_NOACTIVATETIP` | 0x01 | 不激活 TIP | — |
| `TF_TMAE_SECUREMODE` | 0x02 | 安全桌面（UAC/登录界面） | `…TIPCAP_SECUREMODE` |
| `TF_TMAE_UIELEMENTENABLEDONLY` | 0x04 | 仅 UI 元素模式 | `…TIPCAP_UIELEMENTENABLED` |
| `TF_TMAE_COMLESS` | 0x08 | 无 COM 环境（COM 未初始化或 MTA） | `…TIPCAP_COMLESS` |
| `TF_TMAE_WOW16` | 0x10 | 16 位宿主任务 | `…TIPCAP_WOW16` |
| `TF_TMAE_NOACTIVATEKEYBOARDLAYOUT` | 0x20 | 不要切换键盘布局 | — |
| `TF_TMAE_CONSOLE` | 0x40 | 控制台场景（**无对应分类**） | — |

运行期还可以用 `ITfThreadMgrEx::GetActiveFlags()` 查询，并用
`TF_TMF_IMMERSIVEMODE (0x40000000)` 判断当前宿主是不是 Windows 商店/沉浸式应用
（要不要为触屏键盘让位，就看它）。

两个契约细节：

- **`ActivateEx` 的返回值会被 TSF 忽略**——别把失败信息藏在返回值里，
  要写日志/上报。
- 实现了 `ITfTextInputProcessorEx` 并且 `ActivateEx` 被调用时，
  `ITfTextInputProcessor::Activate` **不会**被调用；只有在 `ActivateEx` 失败时
  系统才回退去调 `Activate`。所以 `Activate` 应该写成
  「转调 `ActivateEx(ptim, tid, 0)`」这样的一层薄壳（骨架就是这么做的）。

### 17.2 语言档案里可能出现的全部值名（本机全量统计）

对 `HKLM\SOFTWARE\Microsoft\CTF\TIP\...` 下所有 TIP 做全量统计，
实际出现过的值名有：

| 值名 | 类型 | 说明 |
| --- | --- | --- |
| `(默认)` | REG_SZ | **不是必需的**；本机系统 TIP 基本都未设置 |
| `Description` | REG_SZ | 显示名（骨架一定要写） |
| `Display Description` | REG_EXPAND_SZ | 间接字符串 `@文件,-资源ID`，做多语言 |
| `IconFile` / `IconIndex` | REG_SZ / REG_DWORD | 图标 |
| `Enable` | REG_DWORD | 机器默认启用状态（HKLM）/ 用户实际状态（HKCU） |
| `ProfileFlags` | REG_DWORD | profile 标志（如 0x2 = `TF_RP_HIDDENINSETTINGUI`） |
| `HiddenInSettingUI` | REG_DWORD | 是否在设置界面隐藏（语义未公开） |
| `DisabledOnTransitory` | REG_DWORD | 临时状态下禁用（语义未公开） |
| `RuntimeClass` / `Dword` | REG_SZ / REG_DWORD | 系统 TIP 自用，语义未公开 |

**能用到的就是前六行**，其余是系统内部用的，别照抄。
